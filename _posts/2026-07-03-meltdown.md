## Introduction
Memory isolation is fundamental to the security of operating systems, it is what allows multiple processes to run on the same hardware while preventing each other from being able to access each others data. This also protects the operating system's kernel from processes running in user-space. Memory isolation is enforced by a combination of both operating system controls and hardware controls, such as page permissions and supervisor-only access. These controls are important because operating system security depends on the assumption that user-space processes cannot directly access kernel memory

Meltdown was important because it broke these assumptions, and showed that permission checks alone weren't enough to protect and isolate memory from other processes. Meltdown exploited a CPU performance optimization known as 'out-of-order execution' that temporarily allowed access to protected memory before the processor could handle the permission fault. The visible results of the execution were discarded, however micro-architectural side effects still remained in the CPU cache which could then be inferred using a side-channel technique. This resulted in a user process being able to infer data that should have been isolated by the operating system and hardware.

## Building Blocks
Before we talk about how Meltdown works and why it became such a big deal, we first need to understand the affected components of the system, how they work, and what they aim to do.
#### Memory Space
Memory isolation is one of the core security mechanisms that is used in modern operating systems, it is what prevents other processes from accessing each others memory space and separates user memory from kernel memory. This is important because the kernel has access to the entire system including sensitive information like process memory, and credentials.

Most systems enforce this separation by using a few methods, the first is using virtual memory. Virtual memory give each process its own private address space to use, which is then mapped back to physical memory locations by the operating system. The mapping is done with another layer of enforcement, page tables, where virtual memory is divided up into pages. Page tables then store that mapping and tell the operating system and CPU the mapping of the physical address based on the virtual address. The page table also contains the permissions that are allowed for that memory address such as who can read it, and who can write to it. The last one we're going to mention is hardware enforced privilege checks, the page table also contains a permission to mark kernel memory as supervisor-only. The CPU then checks and enforces these permissions depending on if it is currently running user or kernel code. If user code attempts to access a supervisor-only page the CPU should block it's access and raise a permission fault.

An optimization operating systems commonly used was to map the kernel pages into the virtual address space of each process. By mapping the kernel this way it allowed the CPU to transition faster between kernel-mode and user-mode, as it no longer had to reload the kernel mappings every time it switched, because it was already mapped in the processes page table. To protect the kernel from the user process the operating system would mark the kernel pages as supervisor-only.
#### Out-of-Order Execution
Out-of-order execution is a performance optimization used in modern CPUs to improve efficiency, where instead of executing instructions in the order given by the program, the CPU can look ahead and execute instructions earlier provided it has all the resources it needs to execute. This allows the CPU to continue the stay busy whilst waiting for slower operations, such as memory access. Once the earlier instruction is ready the CPU will then show the architectural result as if the program had executed in the correct order.

Sometimes when executing instructions out of order, the CPU may execute the instructions then realize that they are invalid. In this case the CPU discards them and never commits them to the architectural state. These are known as transient instructions, which is where instructions are temporarily executed but are then discarded by the CPU. Although transient instructions become discarded and never make it into the architectural state, they may still have an affect on the micro-architecture of the system, such as changes to the CPU cache.
#### Flush & Reload
Flush & reload is a side-channel technique that uses timing to infer information from the CPU cache. The CPU cache is another optimization technique used by the CPU to briefly store recently accessed data in case it is needed again. This is so that it can be retrieved faster than it would coming from the main memory, however this creates a timing difference that can be exploited as cached data can be accessed quicker than uncached data.

Flush & reload works by first flushing a specific location on the CPU cache, this is done to create a clean and known starting point reducing the possibility of data being already loaded into cache. After an operation occurs the attacker then reloads the same memory and measures how long the access takes, if the reload is fast it suggests that the location was accessed and stored in the cache.

## Meltdown Explanation
Now that we've explained and understood the building blocks of Meltdown, we can now explain how it works.

First off the process creates a probe array in user memory that contains a value for each possible byte value from 0-255. This array is used as part of the flush & reload method to give the process a way of inferring the data from the cache. The array is flushed from the CPU cache to ensure that the array is not stored there. 

Next the process attempts to read from a protected kernel memory address, architecturally this fails because the process is running in user mode and does not have permission to access supervisor-only memory. However, if this instruction is performed during out-of-order execution, it may temporarily run the instruction before the CPU decides the action is illegal and raises a permission fault. This instruction will then be discarded and never committed to the architecture of the system, becoming a transient instruction.

There is a race condition that exists here, between the instruction being performed and the permission fault being handled. If the instruction can successfully use the protected byte as an index for the probe array, before the permission fault is handled, it may affect the micro-architecture of the system and leave the corresponding array in the CPU cache, even after the permission fault is handled and the instruction is discarded. 

The probe array can now be reloaded with each index of the array getting timed. One index will return a lot quicker than the others, allowing us to infer a single byte of protected memory. By scaling this process across the memory address space we can infer protected memory byte by byte.

However there is a few problems that we need to address first. Normally when a permission fault is issued the process is then terminated, which would stop the exploit from continuing. To get around this we need some form of exception handling. A few methods are to fork the process to perform the out-of-order execution and let the child process crash, creating an exception handler to catch the fault and allow the process to continue, or by using exception suppression with TSX which is an Intel CPU extension that  wraps a group of instructions up as a transaction where if it fails and would raise an exception, it instead discards the transaction and pretends it never happened, without creating an exception.

The next problem is that some operating systems randomize the memory address space of the kernel using Kernel Address Space Layout Randomization (KASLR). To get around this we first need to locate a known value inside the kernel, to do this we can probe different sections of memory until we find a known value. As an example, on Linux at the time KASLR only had 6 bits of entropy, which means there are only 64 possible offsets for the kernel space to be in, which makes this brute-forcing approach viable. Once we find a known value we can find the kernel memory offset by calculating the difference between this address and the equivalent non-randomized address.

By solving these problems we can now use Meltdown to read the protected kernel memory regions in user-space Inferring one byte at a time to infer large portions of physical memory. This may expose things like credentials, or the memory of other applications on the system.

## Impact
The impact Meltdown had on operating system security was huge because it broke one of the basic assumptions these systems relied on; that user-space programs could not read protected kernel memory. Meltdown was also not a normal operating system vulnerability, a operating system could be perfectly implemented and still be vulnerable, because the issue came from the CPU behavior itself.

Some hardware was more affected by Meltdown than others, Intel processors were constantly able to be exploited by Meltdown, whereas Meltdown typically would not work on AMD processors. AMD processors that were tested they were still able to run out-of-order execution, however Meltdown did not work on them.

One of the biggest impacts Meltdown had was to containerized environments. Because containers typically share the same host kernel, Meltdown was able to leak memory across containers. Servers hosting single applications often implemented containers as it was cost effective to do so, however Meltdown running inside of a container is still able to infer memory from the host system as well as from other containers on the system.

## Mitigation
To mitigate Meltdown CPUs had to be redesigned to remove this vulnerability, however this still left existing CPUs vulnerable to the exploit. So some software-based mitigation had to be implemented as well, the most important software mitigation was to remove the kernel mappings from the page table of user processes, known as Kernel Page Table Isolation (KPTI). This stopped Meltdown from being able to read protected memory from the kernel, however this also added overhead into the CPU slowing it down, as it now had to reload the kernel mapping each time it switched.


## Spectre
Spectre was a similar vulnerability that was released alongside Meltdown. It used a different hardware based CPU optimization called speculative execution, where the CPU uses past results to predict what's going to happen next and then executes it ahead of time. If the prediction is wrong then the result is discarded. Spectre is more specific and requires some influence over an existing process, Spectre uses this influence to manipulate the victim process into speculatively executing instructions that access data the victim process has access to, but should not expose. The result is considered a wrong prediction and is discarded, however it has still affected the micro-architecture of the system, such as the cache, and like Meltdown the cache can be manipulated with flush & reload to infer that data.

The discovery of Spectre was just as important as Meltdown was, however whilst Meltdown broke the assumption that programs running in user-space could not read protected kernel memory, Spectre broke the assumption that program enforced bounds checks cannot leak data if they fail architecturally. Spectre was also more specific and generally harder exploit, however it has also been a lot harder to patch and mitigate without removing or undermining the benefits of speculative execution.

## Reflections
Initially I remembered Meltdown and Spectre as a set of vulnerabilities that came out where the patching affected the performance of CPUs. I understood a high level of the what these vulnerabilities were, however I had not fully understood the implications it had on operating system security. By revisiting this vulnerability after learning more about operating systems and how they are secured, I have got to understand Meltdown, and to a lesser extent Spectre, at a much more in depth level and appreciate now why they were such a huge deal at the time. The level of assumptions these vulnerabilities broke is on a similar level of what made other vulnerabilities like Heartbleed and EternalBlue so significant at the time too.

The main take away I had after researching Meltdown is that operating system security cannot only be looked at from a software angle, it's important to also take into consideration the hardware, the way operates, optimizations it might make, and the assumptions that may exist around it. Before Meltdown, it was easy to assume that the current protections in place were enough to stop kernel memory from being leaked or touched by unprivileged processes. Even if illegal access did occur, the assumption became that the CPU discarded the result and not affect the architectural state of the system. Meltdown showed that these assumptions were incorrect and as they did not consider the affects on the micro-architecture of the system, which allowed protected kernel memory to be leaked.

## Conclusion
Meltdown was a significant vulnerability because it showed that operating system security relied on more than just the operating system being correctly implemented. It also broke the assumption that user-space programs could not access protected kernel memory which it did by exploiting behavior in the CPU, leaking the data through the micro-architecture of the system.

The main mitigation technique implemented by operating systems was KPTI. It reduced the risk of Meltdown by removing most of the kernel mappings from the page tables of user processes, however this came with a performance loss. To me this highlighted a trade off that I commonly see in cyber security between performance and security. Because Meltdown is a vulnerability that exists in hardware, for it to be mitigated properly the hardware needs to be redesigned to remove the vulnerability.
